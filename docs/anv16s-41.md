# Acer Nitro ANV16S-41 fan support

Archer now carries **code-level support, awaiting validation on the issue #5
reporter's physical ANV16S-41 / BIOS V1.12**. Compilation and mock tests cannot
prove EC fan response, sensor mapping or profile behavior on that laptop.

## Root cause and protocol evidence

[Archer issue #5](https://github.com/otectus/Archer/issues/5) reports a loaded
Linuwu module without a Sense subtree. At the pinned upstream revision there is
no ANV16S-41 DMI entry. Loading the basic WMI driver does not select a gaming
quirk, so it does not expose `nitro_sense/fan_speed`. Recognizing “Nitro” in
Archer alone cannot fix this.

The exact DMI entry added here is vendor `Acer`, product `Nitro ANV16S-41`.
BIOS V1.12 is the reporter's version, not an artificial version restriction.
Other reports identify board `BRZ_SKF`; issue #5 does not supply its own board
value, so the patch does not invent a board match.

The evidence supports **Linuwu's Nitro v4 gaming WMI implementation**, specifically
the existing ANV16-41 quirk:

- [Upstream issue #61](https://github.com/0x7375646F/Linuwu-Sense/issues/61)
  reports this exact model working with the ANV16-41 quirk, except keyboard
  lighting/button behavior. This is useful model-level evidence, not a detailed
  two-fan validation of BIOS V1.12.
- [PR #127](https://github.com/0x7375646F/Linuwu-Sense/pull/127) likewise selects
  Nitro v4 for this model and separately implements its HID keyboard. It remains
  unmerged in the inspected upstream. Its hardware tests concern RGB; they are
  not proof of both fans. Archer does not import that unrelated HID driver or
  its change to the existing ANV16-41 keyboard quirk.
- [PR #69](https://github.com/0x7375646F/Linuwu-Sense/pull/69) is another unmerged
  v4 DMI proposal, with an unsuccessful interface report. It is not consumed as
  a known-good revision.

Related entries are deliberately not treated as interchangeable:

| Upstream model | Linuwu quirk | Implication |
| --- | --- | --- |
| AMD ANV16-41 | `nitro_v4=1`, WMI four-zone keyboard disabled | Reused for ANV16S-41 based on model-level reports. |
| AMD AN16-41/42/43 | Nitro v4, WMI keyboard enabled | Same fan implementation; different keyboard capability. |
| AMD ANV15-41 and Intel ANV15-51 | `nitro_sense=1` | Reduced Nitro attributes; not grounds to classify every ANV as this variant. |
| Older Nitro legacy | `nitro_sense=2` | No gaming profile registration; not inferred from the “ANV” prefix. |
| Predator v4 | Predator attributes and model-specific keyboard flags | Shares fan implementation; no need to relabel ANV16S-41 as Predator. |

Issue #5 contains GUID3 `61EF69EA-865C-4BC3-A502-A0DEBA0CB531`, gaming GUID4
`7A4DDFE7-5B5D-40B4-8595-4408E0CC7F56`, battery GUID5
`79772EC5-04B1-4BFD-843C-61E7F77B6CC9`, and event GUID
`676AA15E-6A47-4D9F-A2CC-1E6D18D14026`. These agree with the driver interface;
GUID presence alone does not prove command support. No ACPI method bodies or
EC register map are included in the report.

The patch reuses the upstream gaming fan-behavior and fan-speed methods,
percentage encoding and CPU/GPU selectors without introducing new commands or
EC offsets. Before exposing fan control on this model, probe also checks the
existing v4 supported-sensor query for both fan sensors. If the query fails or
only one is advertised, `fan_speed` is hidden and firmware control is retained.
That partial topology needs a further documented hardware report, not guessed
commands. Other models retain their original DMI entries and capability rules.

## Platform profiles

A working `/sys/firmware/acpi/platform_profile` does not establish which driver
owns it. Current [Linux acer-wmi](https://github.com/torvalds/linux/blob/master/drivers/platform/x86/acer-wmi.c)
uses a DMI/override-selected gaming profile implementation; its inspected table
has no ANV16S-41 match. [AMD PMF](https://github.com/torvalds/linux/blob/master/drivers/platform/x86/amd/pmf/sps.c)
is an independent possible provider on this AMD platform. The report's three
profiles are consistent with that possibility, but the provider must be read
from sysfs rather than inferred.

Archer records the actual providers. If an independent provider is present,
`native_platform_profile=1` prevents Linuwu from registering competing profiles
or writing gaming profiles during state restoration and AC events. If stock
`acer_wmi` owns profiles, Linuwu supplies its replacement implementation. Stock
`acer_wmi` and Linuwu must not both own the same platform device.

The `thermal` module reuses an existing provider and never removes the Linuwu
blacklist or forces Predator v4 on Nitro. The GUI follows kernel profile choices
instead of imposing Predator power-source rules on native providers. Profile
changes through Archer first stop curves and restore firmware fans.

## Installation and diagnostics

From the updated Archer checkout, capture the baseline and install:

```sh
python3 scripts/archer-diagnose.py > /tmp/anv16s-before.json
./install.sh --modules driver,gui --verbose --log /tmp/archer-install.log
```

This installs pinned `linuwu-sense/1.0.archer2`, migrates historical Archer-owned DKMS versions,
and requires a reboot. Install headers for **each installed kernel**, including
`linux-zen-headers` for Zen; Clang-built kernels also need `clang` and `llvm`.
If a build or initramfs refresh fails, resolve that failure before rebooting
into the new driver. Archer refreshes mkinitcpio/dracut images; custom boot
images must also be refreshed. Remove any explicit `acer_wmi` force-load from
custom early-boot configuration, since that can bypass a modprobe blacklist.
The source pin/update workflow is documented in [the driver package](../driver/linuwu-sense/README.md).

After reboot:

```sh
python3 scripts/archer-diagnose.py > /tmp/anv16s-after.json
sudo journalctl -k -b --no-hostname -o cat | grep -Ei 'linuwu|Sense quirk|DMI match|ANV16S|paired fans|fan.*fail|platform profile'
sudo journalctl -u archer-daemon -b --no-hostname -o cat | grep -Ei 'Driver diagnostic|Sense base|fan|profile'
```

The diagnostic command is read-only and collects model/vendor/board/BIOS,
kernel, relevant module parameters, WMI GUIDs, profile providers and choices,
Sense attributes/permissions, hwmon fans and Linuwu DKMS state. It does not read
serial numbers, UUIDs, networking information or unrelated logs. Review the
selected journal excerpts before sharing them.

Daemon `driver_status` distinguishes `not_installed`, `module_not_loaded`,
`dmi_unsupported`, `sense_interface_missing`, `fan_node_missing`,
`permission_denied`, `fan_abi_incompatible`, `auto_restore_failed`, and
`supported`. Old drivers without the diagnostic quirk parameter report a missing
interface without claiming to know whether DMI or probe failed. Family detection
never grants fan capability.

## Progressive physical validation

Use an idle laptop on AC, with unobstructed cooling. Keep a temperature/RPM
monitor visible. Stop and restore Auto if a fan behaves unexpectedly, a write
fails, a sensor disappears, or temperatures climb unexpectedly. No stress test
or raw EC/WMI experimentation is needed.

1. **Confirm the driver and match.** Run `dkms status -m linuwu-sense`,
   `modinfo -F version linuwu_sense`, and
   `cat /sys/module/linuwu_sense/parameters/sense_quirk`.
   Expect `1.0.archer2`, `nitro-v4`, and the exact ANV16S-41 DMI match in the
   kernel log. Check that stock `acer_wmi` is not loaded alongside Linuwu.
2. **Confirm Sense creation.** Run
   `ls -ld /sys/devices/platform/acer-wmi/nitro_sense`.
   A family label in the GUI is not enough.
3. **Inspect attributes.** Run
   `ls -l /sys/devices/platform/acer-wmi/nitro_sense`.
   Expect a readable/writable `fan_speed` and kernel log `paired fans=1`.
   If absent, stop here and share diagnostics; do not force a generation.
4. **Establish Auto and RPM baseline.** Stop the daemon to isolate the short
   direct-interface test, then restore Auto:

   ```sh
   sudo systemctl stop archer-daemon
   sudo python3 /opt/archer/archer_daemon.py --restore-fans
   cat /sys/devices/platform/acer-wmi/nitro_sense/fan_speed
   python3 scripts/archer-diagnose.py
   ```

   Expect `0,0`. `fan_speed` is the driver's cached **percentage request**, not
   measured RPM or proof of EC acknowledgement. Inspect the `acer` hwmon fan
   readings and airflow as well. A stationary fan at cool idle can be normal.
5. **Make a conservative CPU change.** Schedule an independent Auto fallback,
   then run this bounded test. Do not proceed unless step 3 passed:

   ```sh
   sudo systemd-run --unit=archer-fan-test-auto --on-active=30s \
     /usr/bin/python3 /opt/archer/archer_daemon.py --restore-fans
   sudo bash <<'SH'
   set -eu
   fan=/sys/devices/platform/acer-wmi/nitro_sense/fan_speed
   test -w "$fan"
   trap 'printf "0,0\n" > "$fan"' EXIT HUP INT TERM
   printf '65,0\n' > "$fan"
   sleep 5
   printf '0,0\n' > "$fan"
   sleep 3
   printf '0,65\n' > "$fan"
   sleep 5
   printf '65,65\n' > "$fan"
   sleep 5
   SH
   ```

6. **Observe both fans.** During those intervals, compare the CPU-only,
   GPU-only, and paired changes with actual RPM/airflow. Zero means **firmware
   Auto**, not stop. Report unexpected coupled behavior or unchanged RPM;
   do not try smaller values or different command encodings to investigate.
7. **Verify restoration.** Run
   `cat /sys/devices/platform/acer-wmi/nitro_sense/fan_speed` and expect `0,0`.
   Wait for the fallback timer to complete, then `sudo systemctl start archer-daemon`.
   In Archer, try Manual 65/65, then Automatic, then
   `sudo systemctl restart archer-daemon`; verify Auto again. Saved manual speeds
   are intentionally not replayed. The service also uses `ExecStopPost` to attempt
   Auto after a crash. A failed EC/ACPI restoration is logged, not guaranteed;
   stop testing and reboot if it cannot be restored.
8. **Compare every native profile.** With curves off and fans in Auto, select
   each advertised profile in Archer, including low-power, balanced and
   performance. Read `platform_profile` and run diagnostics again. Compare the
   provider and choices to the baseline, on AC and then battery. Report rejected
   transitions and disappearing choices. Do not accept losing native profiles as
   a successful fan fix; restore Auto, uninstall the driver and reboot if needed.
9. **Test an Archer curve.** With valid CPU temperature telemetry and the daemon
   running, the existing D-Bus API can start a conservative curve:

   ```sh
   sudo busctl call io.otectus.Archer1 /io/otectus/Archer1 io.otectus.Archer1 \
     SetFanCurve s '{"target":"cpu","enabled":true,"points":[[30,50],[60,65],[75,85],[85,100]]}'
   busctl call io.otectus.Archer1 /io/otectus/Archer1 io.otectus.Archer1 GetFanCurve
   ```

   Observe briefly at idle; repeat for GPU only if it has valid identified
   temperature telemetry. A missing sensor or three consecutive failures stops
   both curves; each failure attempts Auto. Stop explicitly with:

   ```sh
   sudo busctl call io.otectus.Archer1 /io/otectus/Archer1 io.otectus.Archer1 SetFanSpeed ii 0 0
   ```

   The paired ABI means stopping either curve returns **both** fans to Auto and
   disables both curves. Valid explicitly enabled curves can resume on daemon
   restart after an initial Auto reset; stopped/watchdog-disabled curves do not.
10. **Reboot and recheck.** Leave curves stopped, reboot, and capture a final
    diagnostic report. Confirm correct module, Sense subtree, `0,0`, sensible RPM,
    all original profiles and normal Archer controls.

For a failed test, attach the before/after reports, selected log excerpts,
which step failed, the requested pair, and observed CPU/GPU RPM and temperatures.
If profiles regress, `./uninstall.sh` removes Archer's installed components and
restores stock module selection after reboot. It does not remove kernel packages.

## What should go upstream

Propose the exact DMI match with the issue #61/#84/#127 context and new reporter
results, keeping HID keyboard support separate. Offer the generic fan parser,
serialization/Auto restoration, probe-unwind, and native-profile coexistence
fixes separately. Remove Archer's equivalent patches when upstream incorporates
them, update the pinned commit, and bump the DKMS version.
